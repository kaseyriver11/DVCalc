# DVC Companion

## Overview
A web app for Disney Vacation Club owners and renters — started as a points calendar (nightly cost in points and estimated cash equivalent for any resort/room/date) and has grown into a fuller companion covering the rest of DVC ownership: trip planning and saved itineraries, contract tracking and points ledgers, a buying-guide contract-value comparison, and a Trophy Case of ownership/planning achievements. Renamed from "DVCalc" 2026-09-18 to reflect that broader scope — see the Mobile Responsiveness Guardrails section below for one example of a convention that now applies app-wide, not just to the original calendar page.

## Status
**Phase:** Phase 1 complete (core functionality)

## Tech Stack
- **Frontend:** HTML/CSS/JavaScript (vanilla — single-page app, no framework needed)
- **Hosting:** Static files (can be opened locally or deployed anywhere)
- **Data:** JSON embedded in JS (points charts extracted from DVC PDFs)

## Key Features
1. Searchable resort selector dropdown (alphabetical)
2. Room type selector (dynamic per resort)
3. Year selector (2016-2027, historical data for all resorts)
4. Monthly calendar grid with points-per-night displayed
5. Color coding by travel periods (season)
6. Check-in / check-out date selection
7. Side-by-side layout: calendar left, cost breakdown right
8. DVC rental rate slider ($15-$25/point, default $20)
9. Owner mode (calculates cost based on annual dues per point)
10. Summary: total points, rental value, Disney cash rate, savings %
11. Nightly breakdown (expanded by default)
12. Custom cash rate input for non-WDW resorts
13. Responsive design
14. Defaults to current month

## Resorts
All 17 DVC resorts are selectable for 2026 and 2027, and `data.js` now defines all 17 (Animal Kingdom Villas was added 2026-08-30 — see below). Cash rates now cover all 17: the 12 WDW resorts from MouseSavers, Disneyland Hotel from the live pricing pipeline, and Aulani/Grand Californian/Vero Beach/Hilton Head from rough manual estimates (`estimatedCashRates: true` in `data.js` — see `docs/data_reproducibility.md` "Estimated Cash Rates" for methodology and confidence caveats). Every estimated-rate resort gets a "(!)" hover badge (`estimateBadgeHTML()` in `app.js`/`compare.html`) next to its name and on the Cost Comparison tile, explaining the price isn't an observed rate.

**Animal Kingdom Villas** points/cash rates live directly in `data.js` for 2026 only (Jambo House + Kidani Village MouseSavers pages, averaged where both buildings share a view). 2027 has no `data.js` entry — it still comes from the generated `data_historical.js` for points, and falls back to 2026's cash rates via `getCashRateWithFallback()` (same prior-year fallback other resorts use), since MouseSavers' 2027 AKV pages don't yet publish December rates.

All 17 resorts have historical points data back to 2016 (or their opening year) in `data_historical.js`, auto-extracted from DVC Field Guide PDFs. Three gaps exist: BWV 2018 and PVB 2016 are image-based PDFs that can't be text-extracted, and AKV is missing from `data.js` (see `docs/data_reproducibility.md`).

## Data Sources

For detailed data documentation, reproducibility audit, and update instructions, see [`docs/data_reproducibility.md`](docs/data_reproducibility.md).

| Data | Source | How to Update |
|------|--------|---------------|
| Points charts | Official DVC PDFs from Disney's CDN | Run `scripts/fetch_pdf_urls.sh` to get URLs, extract values from PDFs, add to `data.js` |
| Historical points | DVC Field Guide point-archive PDFs | Run `scripts/download_historical_pdfs.sh`, then `scripts/extract_all_historical.py pdfs/` |
| Cash rack rates | MouseSavers.com (WDW only) | Scrape rate tables, map to DVC periods, add as `cashRates` in `wdwPeriods()` |
| Annual dues | dvcresalemarket.com | Update `DUES_PER_POINT` in `data.js` |
| Rental rates | Market observation | Slider is user-configurable ($15-$25/pt) |
| Hotel construction/refurbishment | Disney Food Blog's DFB Disney World Calendar PDF | Re-read the latest PDF, update `data/resort_construction.js` |
| Special events (festivals, hard-ticket parties, runDisney) | Disney Food Blog's DFB Disney World Calendar PDF | Re-read the latest PDF, update `data/disney_events.js` |

## Architecture Notes

### data.js
- `DUES_PER_POINT` — annual dues by resort ID
- `wdwPeriods(rates, cashRates)` / `wdwPeriods2027()` — helpers that create travel period objects for WDW resorts (shared season dates)
- `RESORTS[]` — array of resort objects with `id`, `name`, `year`, `roomTypes[]`, `travelPeriods[]`
- Lookup functions: `getTravelPeriod()`, `getPointsForDate()`, `getCashRateForDate()`

### data_historical.js
- `buildPeriods(periodDefs, rates)` — generic period builder for years with varying structures
- `WDW_YYYY` constants — period definitions (name, color, dateRanges) per year
- Pushes historical resort entries onto `RESORTS[]` (loaded after data.js)
- Covers all 17 resorts, 182 resort-year entries (2016-2027, varying by resort opening date)
- Handles 5-period (2016-2020: Adventure, Choice, Dream, Magic, Premier), 6-period, and 7-period (2021+) structures
- Also handles Aulani flat-rate (SUN-SAT), non-WDW period structures, and variable column counts per resort
- Generated by `scripts/extract_all_historical.py` from PDF source files
- 2026/2027 entries overlap with `data.js`, so the file ends with a `dedupeResorts()` IIFE that keeps the first entry per `(id, year)`. Since `data.js` loads first, its entries win (they include cash rates) and the resort dropdowns list each resort once. The footer is emitted by `extract_all_historical.py`, so regenerating preserves it.

### app.js
- `state` object tracks selections (resort, room type, year, month, check-in/out, rental rate, owner settings)
- Calendar renders a 7-column grid with the point cost as each cell's centered hero number and the cash rate as a smaller line right under it; the date number, crowd score, and 🎉 event icon are each pinned to their own corner of the cell (top-left/top-right/bottom-right) so they can't collide. The 2026-09-19 declutter pass had dropped the cash rate entirely and swapped the 🎉 for a plain corner dot, but both were reverted the same day on user feedback that it read as "too boring" — the SUN-THU/FRI-SAT sub-label stays dropped, though, since the day-of-week header already conveys that
- Summary panel shows totals with conditional sections based on available data
- Year-aware: `getResort()` filters by both `resortId` and `year`
- Calendar cells show a 🎉 badge (bottom-right corner) only for genuinely date-specific entries from `getEventsForDate()` (`data/disney_events.js` categories `hardTicketEvent`/`runDisney`/`singleDay` — not `festival`/`seasonal`, see `BROAD_EVENT_CATEGORIES`), with a hover tooltip listing them — credited to Disney Food Blog. This scoping (kept from the 2026-09-19 declutter pass even after the emoji itself came back) is what keeps a multi-week festival from painting the badge across all 30+ days it runs; that broader window is surfaced once instead, in the "Special Events & Festivals" summary card (`buildSpecialEventsHTML()`)
- The summary panel shows a "Resort Alerts" card (`buildResortAlertsHTML()`, sourced from `data/resort_construction.js`) whenever the selected resort has known ongoing/upcoming construction or refurbishment; entries overlapping the selected stay dates are called out with a "During your stay" badge. Alerts render *before* "Your Stay" while browsing (no dates picked yet) as a "consider this while picking a date" prompt, but move to *after* it once dates are selected, so they read as supporting context rather than the top-billed card
- "Booking As" (contract picker) and "Load Trip" (saved-itinerary picker) live in the top control bar (`#booking-as-control`/`#itinerary-load-control` in index.html) as real `initCustomSelect()`-driven custom-selects — same persistent-`<select>`-plus-styled-trigger component Resort/Room Type use, not a plain native `<select>` — so they match the theme and the trigger's fixed width (narrow for Load Trip) keeps long names from blowing out the control bar; the dropdown's option list still shows full names (wrapping, not truncating). `renderBookingAsControl()`/`renderItineraryLoadControl()` repopulate `contractSelect`/`itineraryLoadSelect`'s `<option>`s and call `._customSelectRender()` — the same one-time-`initCustomSelect()`-then-repopulate pattern as `populateRoomTypes()`/`roomSelect`, not a full innerHTML rebuild. The old "Points Year" dropdown was removed entirely — crossing a year boundary is only reachable by paging months now (`prevBtn`/`nextBtn` already handled that boundary; `state.year` is otherwise unchanged). Only the per-stay eligibility/points feedback (`buildContractEligibilityHTML()`) lives in the "Your Stay" card, not the top bar
- **Multi-Contract Split** (`buildContractEligibilityHTML()`, same function as above — living there means both `renderSummary()` and `renderTripRail()`/review mode get it for free): with 2+ active contracts, real dates picked, and a single-resort stay (never during an actual split STAY across resorts — `multiContractSplitMode` is named deliberately unlike `isSplitMode()` to keep those two "split" concepts apart in code and copy), a "Split points across contracts instead →" link toggles from the normal single-contract Smart Draw view into `buildMultiContractSplitHTML()`: one `<input type="range">` slider per contract that can book the resort at all (`eligibleSplitContracts()` — a contract that's hard-blocked from this resort, e.g. resale-restricted to a different home-only resort, is left out entirely; that's a different case from a 7-month contract whose window just hasn't opened yet, which still gets a row). Dragging a slider updates that row's own numbers and the shared totals line via direct DOM writes (`updateMultiSplitRowLive()`), not a full re-render, so the slider doesn't lose its drag state — same reasoning as account.html's `updateLedgerRowTotal()`. Defaults to a greedy fill (drain the first eligible contract before touching the next, mirroring `computeSmartDraw()`'s own bucket-priority spirit one level up) rather than starting every slider at zero, since sliders are for overriding a starting point, not building one from nothing. "Apply Split" is disabled until the total allocated exactly equals the stay's point cost (no partial-payment concept for one reservation) and, once enabled, runs `computeSmartDraw()` **per contract** against its own slider amount (so each contract still draws Holding→Banked→Borrowed→Current internally) and writes every result via the same `upsertContractYearPoints()` Smart Draw and the ledger itself use — with a combined Undo snapshot across every touched contract, same 8-second visibility window as Smart Draw's own undo. Item 2 of the task this shipped from ("alert if non-home resort points are allocated before the 7-month window opens") is `contractWindowNotYetOpenWarning()` — shown per-row (regardless of whether that row currently has any points allocated, so the warning is visible before the owner even touches that slider) whenever `getContractWindowMonths()` returns 7 and the stay's check-in date is still beyond `monthsFromTodayCutoff(7)`; the warning states the actual date the window opens (`monthsBeforeCheckIn()`), not just that it's closed
- **11-to-7 Swap Simulator** (also in `buildContractEligibilityHTML()`, same one-function-covers-both-render-paths reasoning as Multi-Contract Split above): only offered when the currently-browsed resort IS the selected contract's home resort (`getContractWindowMonths() === 11`) and real dates are picked -- modeling the common DVC strategy of confirming home resort at 11 months as a safety net, then trying to swap to somewhere else once the 7-month all-resorts window opens. A "Planning to swap at 7 months?" toggle (`swapSimulatorMode`) reveals two `.custom-select` pickers (target resort, then that resort's room types -- `attachSwapSimulatorListeners()` calls `window.DVCUI.initCustomSelect()` on both after every render, from inside `attachStayActionButtonListeners()` so it's covered by every call site that already invokes that) and, once both are picked, shows: the exact 11-month (home) and 7-month (swap) window-opening dates (`monthsBeforeCheckIn()`, the mirror image of `monthsFromTodayCutoff()` -- that one answers "is the window open yet," this one answers "what date does/did it open"); the Point Delta between the two stays' point costs (`computeStayEntry()` on each, reused as-is); and a borrowing-risk read. That risk calc deliberately does NOT reuse `computeSmartDraw()` -- a first pass did, and shipped a real bug (caught the same day, before users saw it) where it understated what a contract could cover, because `computeSmartDraw()` only draws from whatever's already RECORDED as borrowed in the ledger rather than the contract's actual borrowing ceiling. The fix models borrowing as elastic capacity instead: `nonBorrowedAvailable` (remaining+banked+holding) covers what it can, and whatever's left for each of the two stays is compared against `maxBorrowable` (`contract.points_per_year`, same proxy `validateBorrowedPoints()` uses). `extraBorrowNeeded` is the swap-specific delta in borrowing requirement (target's shortfall minus home's own shortfall, so a contract that already needs to borrow for the unswapped home stay isn't double-counted); a danger guardrail fires instead if even the target's own shortfall alone exceeds `maxBorrowable` outright. The warning copy is accurate to DVC's real rule (confirmed via DVC Resale Market/DVC Rental Store, 2026-09-19 research): borrowing is a final transaction, points can't be moved back to next year even if the trip that prompted the borrow falls through -- so an unnecessary borrow for a swap that doesn't pan out isn't recoverable, just left over. (This same research is what caught `dvc-ledger.js`'s `MAX_BORROW_RATIO` bug above.)
- **Two-phase layout ("review mode")**: once a complete single-resort stay is picked, `isReviewMode()` (`!isSplitMode() && getStayDates().length > 0 && !forceExpandCalendar`) collapses the full calendar into a compact "trip rail" card (`renderTripRail()`, into `#trip-rail-view`) — resort/room, dates, a mini per-night points strip laid out as a real 7-column CSS grid with leading blank cells (so it lines up by day-of-week like the full calendar and every night stays equal-width, instead of a flex-wrap approach where a partial last row's items stretch to fill it), points, contract eligibility, then Edit dates/Clear Selection/Add Another Resort/Compare All Resorts/Save Itinerary all stacked together (the shared `buildStayActionButtonsHTML()` + `attachStayActionButtonListeners()` — also used by the normal `#action-buttons` slot in non-review layouts). The summary panel expands (`.summary-side.expanded`) into: Cost Comparison leading, then Stay Insights full-width (its `<h3>` and the "Find Alternatives" button share a `.card-header-row` — title left, button right, instead of the button stacked full-width below the card's content), then Booking Outlook, Special Events & Festivals, and Resort Alerts stacked full-width in that order (the old side-by-side `.insights-columns`/`.insights-col` pairing of Booking Outlook with Crowd Forecast was removed 2026-09-19 along with Crowd Forecast itself — Booking Outlook had no remaining partner card, so it just renders full-width now) — Resort Alerts' own entries still lay out via `.resort-alert-list`'s `auto-fit`/`minmax(240px, 1fr)` grid, so multiple alerts sit two-up once the card's wide enough instead of always stacking single-file. No separate "Your Stay" card in review mode — the trip rail already covers it. `forceExpandCalendar` resets to `false` (re-collapsing) whenever a fresh stay gets completed or cleared; clicking the *current* check-in date again while a complete range is showing clears both dates outright (`handleDateClick()`) rather than re-priming checkIn to the same value, which would otherwise silently turn the next click into a checkout instead of a fresh check-in. Split-stay mode never enters review mode — the full calendar and original action-buttons placement stay unchanged there. `renderLayoutMode()` (tail of `renderCalendar()`/`renderSummary()`) toggles `#full-calendar-view`/`#trip-rail-view` visibility. The Cost Comparison "If booking through Disney" tile folds its own custom-rate input inline (`showCustomRateInput`/`showDisneyTile` in `renderSummary()`) rather than showing a separate input block above the tile grid — same `.cost-tile-rate-input` pattern the rental tile already used. That input is a fallback for resorts with NO published cash rate at all (non-WDW) — it doesn't appear for a resort that has real rate data, even if that number looks surprising; see `data/data.js`'s per-period `cashRates` for the actual stored Sun-Thu/Fri-Sat figures. The trip rail's mini strip also shows 2 dimmed/dashed "context" days just outside the stay on each end (computed fresh each render, so they always sit just past whatever the current edges are) — clicking one extends check-in/check-out to include it, and clicking the first or last *real* night removes it (shrinking that edge inward, or clearing the whole selection if it was a 1-night stay), all via `adjustTripEdge()`. Interior nights aren't clickable — removing one would split the stay into two ranges, which the single check-in/check-out model can't represent
- **Special Events & Festivals** (`buildSpecialEventsHTML()`, 2026-09-19, replacing the old standalone Crowd Forecast card — crowds are already benchmarked in Stay Insights' distribution chart and on the calendar cells' own crowd badge, so a third restatement didn't earn its space) sits directly above Resort Alerts and filters `getEventsForDate()` against the picked stay window: broad `festival`/`seasonal` windows list once as "Active Festivals" with their full running range (e.g. "Aug 27 – Nov 21"), while date-specific `hardTicketEvent`/`runDisney`/`singleDay` entries list under "Date-Specific Events" with the exact stay nights they land on (e.g. "Active on Sep 11, Sep 15"), each tagged with a category badge. Shows an explicit empty state ("No major festivals or ticketed events scheduled during this stay.") rather than disappearing, so its absence from the panel always means "checked, nothing found" rather than looking broken. Not shown for non-WDW resorts (`NON_WDW_RESORT_IDS`) since these are all Walt Disney World park events
- Stay Insights' three distribution bars (`buildDistributionHTML()`) color their "current stay" bar green-to-red (`distGoodBadColor()`, keyed off the same percentile the callout text already shows) for Crowd forecast and Points cost only — both are unambiguous "lower is better," so a calm/cheap stay reads as green at a glance instead of needing the percentile sentence to know if a low number is actually good. Cash price stays neutral purple deliberately: the Value Score right above these bars treats a *high* cash-per-point as the favorable direction (better rental value), so coloring raw cash red-for-expensive would visually contradict that
- The "Find Alternatives" modal's "Also check other resorts" toggle (`state.altCrossResort`) reveals a second "WDW (Orlando) only" checkbox (`state.altWdwOnly`) that restricts cross-resort candidates to `NON_WDW_RESORT_IDS`-excluded resorts, same set and same filtering approach `compare.html`'s own WDW-only toggle uses. Only shown once cross-resort search is on — filtering by region is meaningless when the search is already scoped to a single resort
- Every `tooltip-anchor` (crowd/value/distribution hovers, calendar day cells, trip rail chips, booking outlook dots) gets its `cursor: pointer` and `user-select: none` from the shared base rule in `styles.css`/`compare.html`, not per-element — a bare span/div with text or an emoji directly inside it (a crowd number, a 🎉, a value-score badge) otherwise falls back to the browser's default text-select (I-beam) cursor on the glyph itself even with a pointer-cursor ancestor, since `cursor: auto` resolves per-content rather than by inheritance. Keeping it on the base class is what makes every hover in the app look and feel the same instead of drifting element by element

### compare.html (self-contained)
- "WDW (Orlando) only" checkbox (`state.wdwOnly`) filters the resort list to exclude `NON_WDW_RESORT_IDS` (aulani, hiltonHead, veroBeach, disneylandHotel, grandCalifornian) — that set already existed for the Booking Outlook seasonal-period logic, reused here for the resort filter too

### suggest.html (self-contained)
- Input is a 3-step accordion wizard (`renderWizard()`, `wizardStep` 1-3, plus a `4` "done" sentinel), not a static all-at-once form — Points, Year & Travel Window → Room Type & Party Vibe → Stay Length & Scope. Only the active step's body is ever in the DOM; completed steps collapse to a tap-to-reopen summary row (`collapsedStepHTML()`), steps not yet reached render dimmed (`upcomingStepHTML()`). All wizard state lives in one `wizardData` object (not read from scattered DOM fields at submit time) — `runSearch()` reads directly from it. `wizardStep = 4` is a "done" sentinel meaning "collapse all three steps," not a real step; every `s < wizardStep` check in the render loop is naturally true for all of 1-3 at that point, so no special case is needed to fully collapse the wizard after a search.
- Year and Travel Window live in the SAME step (step 1), not separate steps, and their choices constrain each other — `availableMonthsForYear(year)` hides months before "today" whenever the selected year is the current real year (a future year has no such restriction), so picking 2026 in September never offers April. Changing the year `<select>` fires a real "change" event (`dvc-ui.js` dispatches one from the custom-select, same as a native select) that re-renders step 1 and resets `wizardData.month` to "any" if the previously-picked month is no longer valid for the newly-selected year. `findFeasibleStays()` has the same guard independently (`TODAY_STR` filter on generated `startDates` when `year === currentRealYear`) so "Any month" for the current year can't generate already-past candidate dates either — the UI restriction and the search restriction are two separate, deliberately redundant checks, not one relying on the other.
- `minNights`/`maxNights` default to **5/7**, not 1/14 — the old 14-night ceiling meant almost every resort/room combo maxed out its greedy `maxNightsWithinBudget()` extension into one long "marathon" stay, which is what actually caused the old ~128-result bloat, not a flaw in the underlying feasibility algorithm (unchanged, and still documented as the correct max-nights answer for a single continuous stay). Capping the default window to a realistic vacation length was sufficient; no change to `findFeasibleStays()`'s search logic was needed.
- Deliberately does NOT use the dual-view Mobile Card Feed pattern (table for desktop, cards for mobile below a breakpoint — see guardrail #7 and `contractvalue.html`) — results render as `.result-card`s at every viewport, with no `<table>` in the DOM at all (see the 2026-09-18 mobile-first overhaul). This page's rows only ever carry 3 real metrics (Nights, Points Used, Points Left) plus a date range, so unlike `contractvalue.html`'s dense 8-column ranking table, there's no desktop dense-scan use case a table would serve that the card stack doesn't already cover. Sorting is one pill toolbar (`buildSortToolbarHTML()`, `.sort-pill` buttons) shared by all viewports — no header-click-to-sort affordance exists since there's no table.
- Results default to sorting by `pointsPerNight` ascending ("Best Value") rather than `nights` descending — each result also carries a `pointsPerNight` field (`pointsUsed / nights`, computed in `findFeasibleStays()`) purely for this sort; it's not shown as its own card metric since the card's stats block is deliberately just the 3 fields above. Only the top `DEFAULT_RESULT_LIMIT` (20) render initially regardless of total match count — a "Show all N stays" button (`showAllResults` flag) reveals the rest on tap rather than hiding them permanently, so "curated by default" never means "data withheld."
- `renderResults()`'s empty state (`buildEmptyStateHTML()`) is context-aware: it reads `lastParams` (points/minNights/scope/category from the most recent `runSearch()`) to only surface a "try this instead" recovery button when that filter is actually the kind of thing loosening it would help (e.g. "Search all resorts" only appears if scope isn't already "all"). Its buttons mutate `wizardData` directly and re-call `runSearch()` rather than routing back through the wizard steps.
- The Points Year field uses the shared `.custom-select` component (`tokens.css` + `dvc-ui.js`, same markup/JS as `index.html`'s Resort/Room Type pickers) instead of a bare `<select>`, per the native-select ban in `README.md`. Because step 1's whole body is rebuilt via `innerHTML` on every `renderWizard()` call, `window.DVCUI.initCustomSelect()` is re-run on the fresh `<select>` node each time step 1 renders — unlike `index.html`'s persistent selects, which instead call the cached `._customSelectRender()` to repopulate without re-init. The "Resorts I can book" scope toggle in step 3 is a plain two-way toggle (all vs. access), not three-way — the old "My home resort(s) only" option was dropped in the mobile-first redesign.
- "View This Stay" (in `renderResults()`) hands off to `index.html` two ways: the existing one-shot `dvc_calendar_state`/`dvc_return_to_calendar` pair (consumed and cleared by `app.js` on load, restores the actual calendar selection) AND a separate, NOT one-shot `dvc_suggest_state`/`dvc_suggest_return` pair that `index.html`'s "Back to Suggest a Stay" banner (`styles.css`, wired in `app.js`) uses to link back here. `dvc_suggest_state` holds `{ wizardData, sortKey, sortDir, showAllResults }` — not `lastResults` itself, since results are always deterministically recomputed from `wizardData` via `runSearch()` on restore rather than duplicating storage of derived data. Both keys are consumed (read once, then removed) the moment suggest.html successfully restores from them; a fresh "View This Stay" click re-sets both for the next round trip regardless.

### contractvalue.html (self-contained)
- Input is the same 4-step accordion wizard pattern as `suggest.html` (`renderWizard()`, `wizardStep` 1-4, `5` = "done" sentinel) — Purchase Intent & Channel → Target Point Budget → Primary Room Category → Usage Horizon & Vibe — replacing what used to be a single static form showing every input (including "advanced" ones like closing cost and dues growth) at once. All the actual valuation math (`computeRow()`, `sortRows()`, `bestIndices()`, `medianRoomPoints()`, the breakeven-horizon loop) is UNCHANGED from before this rewrite — only the input/results presentation layer changed. `computeRow()` reads `wizardData.purchaseType`/`wizardData.category` directly (no more standalone `purchaseType`/`category` module variables).
- Closing Cost and Dues Growth are NOT wizard steps — they default to 1500/4.0 (with the same resale/direct auto-adjust rule as before: only touched if still at either default, so a manual edit survives toggling purchase type back and forth) and live in a collapsed-by-default "Adjust assumptions" panel (`showAdvanced`, `.advanced-panel`) inside the results view instead, per the redesign's explicit goal of not surfacing advanced financial parameters until asked for.

## Mobile Responsiveness Guardrails

Checklist for any new page or component, established 2026-09-18 after two rounds of real mobile bugs (calendar/legend/controls-bar overflow on index.html, then crushed multi-column forms and an illegibly-squeezed table on contractvalue.html/suggest.html/itinerarycompare.html):

1. **Multi-column form grids collapse to 1 column, not 2, under `max-width: 700px`.** An intermediate 2-column tier still crushes a labeled dropdown or a 3-4-button toggle into an unreadable sliver on a real phone. `grid-template-columns: 1fr` is the only mobile value that's actually safe — see `contractvalue.html`/`suggest.html`/`itinerarycompare.html`'s `.form-grid`/`.picker-row` rules.
2. **A horizontal-scroll table is only acceptable for a genuinely narrow table (≤5 columns)** — `.amort-table` (5 cols) and `.compare-table` are fine with `overflow-x: auto` + `table-layout: auto` (content width naturally forces the scroll). **A wide/dense data table (6+ columns of ranked or comparison data) gets a Mobile Card Feed instead, not a scrolling table** — see rule 7. A multi-column spreadsheet is the wrong shape for a phone screen no matter how it's scaled or scrolled; squeezing/scrolling it was tried twice on `contractvalue.html`'s "Ranked by Value" table and rejected both times as still feeling like "a zoomed-out desktop website."
3. **Never pair `table-layout: fixed` with `width: 100%`** on any table, mobile or not — fixed layout divides that 100% among every column regardless of viewport, silently crushing each one instead of scrolling or wrapping.
4. **A flex container switching to `flex-direction: column` on mobile also needs `align-items: stretch`** if any child relies on `width: auto` — a desktop `align-items: flex-start` (common for top-aligned sidebar layouts) lets that child shrink-to-fit its own widest content instead of the viewport once it's stacked, which silently reintroduces horizontal overflow. This bit `index.html`'s `.main-layout`/`.summary-side.expanded`.
5. **Never rely on `Ctrl+Shift+M` alone to check this** — it only toggles DevTools' device toolbar when DevTools already has focus; otherwise Chrome intercepts it as the profile-switcher shortcut. Open DevTools (F12) first, then the device toolbar icon or the shortcut.
6. **Before calling a page mobile-ready, verify at ~375-390px width in TWO states**: the page's default/empty state, and after completing its main interactive flow (selecting a stay, submitting a form, opening a modal) — new wide elements often only appear once real content renders (this is exactly how the Cost Comparison/Stay Insights overflow above was missed initially). The check itself: `document.documentElement.scrollWidth === document.documentElement.clientWidth` should hold in both states; if it doesn't, walk `document.querySelectorAll('*')` for any element whose `getBoundingClientRect().right` exceeds the viewport width to find the actual offending element rather than guessing.
7. **Mobile Card Feed pattern for wide/dense tables** (established on `contractvalue.html`'s "Ranked by Value", 8 columns): build BOTH the `<table>` and a parallel `.{page}-cards` div from the same sorted data array in one render function, and let a single `@media (max-width: 768px) { .results-table-wrap { display: none; } .results-cards { display: flex; } }` rule decide which one shows — never a JS-side branch on viewport width, and never a second copy of the render logic. Each card: a header (primary identity + status badges), one **hero metric** in a large bold callout (the same single column the desktop table highlights as "best," e.g. with a checkmark/color), then the remaining metrics in a `grid-template-columns: repeat(2, 1fr)` key/value micro-grid — never another scrolling row of columns. Any interactive cell (an editable price input, a reset button) reuses the exact same class name and `data-*` attributes in both the table and card markup, so existing `document.querySelectorAll(".foo")`-based event wiring picks up both copies automatically — don't write a second wiring path for the card version. If the table has column-header click-to-sort, add a mobile-only `<select>` (`.mobile-sort-control`, hidden on desktop, shown under the same 768px query) that sets the same `sortKey`/`sortDir` state and re-renders, since the card view has no header cells to click.
8. **A hidden tooltip/popover can inflate `scrollWidth` even though nothing is visibly overflowing.** `.tooltip-card` (tokens.css) sits at `visibility: hidden` until hover, not `display: none` — hidden-but-present elements still generate a layout box, and if that box's TEXT inherits `white-space: nowrap` from an ancestor that set it for its own unrelated reasons (`.wallet-card-deadline-pill` needed nowrap for its own one-line label; `.tooltip-card` nested inside it inherited that too), a normal sentence-length tooltip renders as one ~800px+ invisible line and silently adds horizontal scroll to the whole page. `getBoundingClientRect()` on the tooltip itself won't catch this (its reported box still looks small/contained) — only `element.scrollWidth` vs `offsetWidth` reveals it. `.tooltip-card` now sets `white-space: normal` explicitly so this can't recur, but the general lesson: any shared hidden-until-interaction component should set every inheritable text property (`white-space`, `text-align`, etc.) explicitly rather than trusting whatever ancestor it happens to get nested inside next.
9. **Grid, not flex, for a row of equal-width stat boxes.** `flex` with no explicit `flex-basis`/width sizes each child to its own content — for a box wrapping an `<input>`, that resolves to the input's own default browser intrinsic width (~170-190px), not something that shrinks for a phone. Three such boxes fit fine on desktop and wrap into oversized single-column blocks on mobile ("looks like a form" was the actual bug report — `account.html`'s Banked/Current/Borrowed ledger). `grid-template-columns: repeat(3, 1fr)` forces every item into an even, viewport-relative share of the row at any width and fixes this without a media query at all.
10. **A `.tooltip-anchor`/`[data-tip]` tap-to-toggle delegate must run on the CAPTURE phase and call `e.stopPropagation()`, not just listen on bubble.** Found on `compare.html`/`contractvalue.html`: their column-header info-icon tooltips sit inside a `th[data-sort]` that has its own click-to-sort listener. A bubble-phase `document.addEventListener("click", ...)` delegate runs AFTER that `th` listener already fired (bubbling goes target → th → document), so by the time the delegate tries to flag the tapped icon with `.tap-open`, the `th`'s own handler has already re-rendered the table and detached that exact node — the tap-open class lands on a dead element the live DOM no longer contains, so the tooltip never visibly opens on a real tap. Registering the delegate with `{capture: true}` (fires document → ... → target, before the bubble phase reaches the `th`) and calling `e.stopPropagation()` once a real anchor is found fixes it, and has the added benefit of not sorting the column just because the user meant to read its tooltip. Any new tooltip-anchor nested inside another element with its own click handler needs this same treatment — a plain bubble-phase delegate only happens to work when the anchor has no clickable ancestor of its own (true for badges/dots, not true for header info-icons).
11. **Tooltip/hover-card body text must be 1-2 short sentences, not a paragraph.** `contractvalue.html`'s `METRIC_TIPS` originally ran 60-90 words each (written like code comments explaining *why* a formula works a certain way, not like end-user help text) — on a narrow card this wraps into 8-10 lines, which is both unreadable and, combined with guardrail below, gets clipped off-screen. Say what the number IS and, if truly needed, the one thing that makes it useful — cut the justification/rationale entirely, that belongs in a code comment near the calculation, not in the UI. **Separately:** a tooltip/hover-card that's always centered under its anchor (`left: 50%; transform: translateX(-50%)`) overflows off-screen once the anchor sits near the edge of a narrow container — confirmed by a user screenshot showing the leftmost stat's tooltip clipped on the left and the rightmost stat's clipped on the right, on the exact same card. `tokens.css`'s `.tooltip-anchor` component already has `.tooltip-align-left`/`.tooltip-align-right` modifiers for this; `contractvalue.html`'s bespoke `[data-tip]` mechanism got its own copy (`.tip-align-left`/`.tip-align-right`, same naming) applied to the first/last item in a row of stats. Any new multi-item row of tooltipped stats needs the edge items aligned this way from the start, not centered by default.
12. **`align-items: stretch` does NOT clamp a flex item back down to its container** — an item whose content-based minimum is wider than the container overflows it anyway, and (this is the part that makes it look like a whole-page bug rather than one bad element) *every sibling* then stretches to that same overflowed width, so the entire control bar, and with it the page, scrolls sideways. Found 2026-09-21 on `index.html`'s control bar: a long contract name in "Booking As" ("The Villas at Disney's Grand Californian Hotel & Spa") made all four control groups 412px wide inside a 353px container at 390px viewport. `min-width: 0` alone does NOT fix this — an explicit `max-width: 100%` on the stretched item is what actually caps it (`.control-group` in `styles.css`). Pair it with `flex: 1; min-width: 0` on the truncating text span itself, or the `text-overflow: ellipsis` never fires: a flex item's default `min-width: auto` refuses to shrink below its own min-content, which for `white-space: nowrap` text is the whole string. And any badge/pill that must survive the truncation has to be a SIBLING of that span (`flex-shrink: 0`), not nested inside it — nested, it's the first thing the ellipsis eats.
